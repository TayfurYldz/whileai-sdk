# Hill-Climbing Text-to-SQL with a Verifier as the Reward: Five Checkpoints, Every One Measured

**TL;DR.** We built a text-to-SQL training loop where the reward is a program:
run the model's query on a seeded Postgres database and compare the result
set to the gold query's. No judge. Then we tried to make a 4B model climb on
it: self-distillation, three chained GRPO rounds, one aggressive variant.
Every checkpoint was measured the same way, on the same 140 held-out tasks,
four samples each, as a paired pass@1 with a 95% interval. The honest result:
0.58 to 0.62 after three chained rounds, an interval that still touches zero,
two secondary numbers that clearly moved, and a loop that now runs fast enough
to keep going. The dataset, every checkpoint's
rollouts and every adapter are on Hugging Face at
[`zero-proof-ai/text-to-sql-shop`](https://huggingface.co/datasets/zero-proof-ai/text-to-sql-shop);
the code is the
[`recipes/04-train/text-to-sql`](https://github.com/Zero-Proof-AI/zeroproof-sdk/tree/main/recipes/04-train/text-to-sql)
recipe in the open-source [zeroproof SDK](https://github.com/Zero-Proof-AI/zeroproof-sdk).

## The setup

**Schema.** An online store: `categories`, `products`, `customers`,
`employees`, `orders`, `order_items`, `payments`, `reviews`. Eight tables,
300 orders, generated by a seeded script so anyone can rebuild the exact
database. The traps are the ones real schemas have: `shipped_at` is NULL
until an order ships, `discount_pct` is NULL when there was no discount,
cancelled orders have no captured payment, a refund is a second payment row,
categories and employees reference themselves.

**Tasks.** 741 question/gold-SQL pairs, written by Claude Sonnet 5 with the
schema, the notes a new analyst would need, and a data inventory in front of
it, across ten archetypes (single-table aggregation, top-N, two-table join,
multi-table join, GROUP BY with HAVING, NULL semantics, self-joins, dates,
anti-joins, derived metrics) and three difficulties. Every gold query was
executed twice and kept only if it returned 1 to 50 stable rows; near
duplicates were dropped. 140 tasks are held out by a hash of the task id, so
every script agrees on the split and no run ever sees them.

**Verifier.** `SQLExec` extracts the query from the reply, runs it read-only
with a statement timeout, and compares result sets Spider-style: same
multiset of rows, floats rounded to two places, text case-folded, columns in
any order, ordered only when the gold has `ORDER BY`. It is a
`zeroproof.simulations.verify.Verifier`, so it drops into `data.grade`,
`optimize` and the publish gate where an LLM judge would, and the gold lives
in `privileged.reference`, which the training export never projects.

**Measurement.** Every checkpoint is sampled on the holdout through
`zps.simulate(agent, tasks=..., repeats=4)`, graded by the verifier, and
compared to the base with `zps.delta_report`: a paired bootstrap over tasks,
95% interval, by difficulty and by archetype. The rule we hold ourselves to:
a claim is a number with an interval on a set the model never trained on.

## Read the headroom before training anything

The first thing the SDK tells you is whether RL can move at all. pass@4
minus pass@1 is the headroom a grouped update can amplify: the share of
tasks the policy can already solve sometimes but not reliably.

| Model (81-task holdout, first cut) | pass@1 | pass@4 | headroom |
|---|---|---|---|
| Qwen3-4B, thinking off | 0.58 | 0.64 | 0.06 |
| Qwen3-4B, thinking on | 0.69 | 0.81 | 0.12 |
| Claude Haiku 4.5 | 0.72 | 0.75 | 0.04 |
| Claude Sonnet 5 | 0.88 | 0.90 | 0.02 |

With thinking off, 0.06 of headroom predicted that nothing would move, and
nothing did: hosted SFT on 336 gold demonstrations went 0.58 to 0.63 and 300
steps of GRPO went 0.58 to 0.59, both intervals covering zero. So the climb
happens in thinking mode, where the same weights start at 0.69 and can reach
0.81 one sample in four.

## The checkpoints

After the first cut we authored 324 more tasks on the archetypes the model
fails (multi-table joins, self-joins, date buckets, derived metrics), which
grew the holdout to 140 tasks and narrowed the interval to about six points.
Everything below is on that holdout, sampled through the SDK path with a
4,096-token reply budget and thinking on.

| Checkpoint | From | Method | pass@1 (95% CI) | pass^4 | emits a query |
|---|---|---|---|---|---|
| base | Qwen/Qwen3-4B | - | 0.58 (0.52..0.64) | 0.31 | 0.86 |
| r1 | base | GRPO, 100 steps, lr 2e-5, HF generate | 0.58 (0.52..0.64) | 0.29 | 0.89 |
| r2 | r1 | GRPO, 200 steps, lr 5e-5, beta 0.01 | 0.60 (0.54..0.67) | 0.34 | 0.90 |
| sft-think | base | self-distillation: 199 verified thinking traces, hosted SFT | 0.60 (0.54..0.67) | 0.39 | 0.96 |
| r3 | r2 | GRPO, 1,000 steps, vLLM generation, 8 prompts per generate | 0.62 (0.55..0.68) | 0.34 | 0.87 |

Every checkpoint's holdout rollouts are an `eval-*` config in the dataset
repo, and every adapter is a model repo (`zero-proof-ai/text-to-sql-shop-r2`
and so on), so each row of this table can be re-derived.

## What moved and what did not

**pass@1 moved a little, and only at the end.** The chain reads 0.58, 0.58,
0.60, 0.62: round 3, the first round with a real dose (1,000 steps, three
passes over the prompts), is +0.03 over the base with an interval of
-0.02..+0.08, up at every difficulty, and still not a proven climb by our own
rule (the interval has to exclude zero). That is the result, and it is worth
saying plainly because the training curves say something else.

**The training reward moved more than the holdout.** Round 1 went from 0.49
to 0.63 over its last 25 steps, round 2 sat at 0.60 to 0.75 with KL climbing
to 0.08, round 3 held 0.58 to 0.64 with every group mixed (gradient every
step) and ended at 0.81 over its last block. A training reward that rises
faster than the holdout means the policy is getting better at the prompts it
is shown before it gets better at ones it is not; at 800 to 2,400 samples
over 336 prompts with LoRA rank 16 that gap was the whole story, and at 8,000
samples over 601 prompts it started to close.

**Two things it learned first were cheap.** Thinking length fell from about
1,090 to 800 tokens in every round: shorter reasoning is the first thing a
length-capped reward teaches. And self-distillation fixed the model's habit of
thinking without answering: the share of replies that emit a query went from
0.87 to 0.96, the one change in the table with an interval that excludes
zero, and pass^4 (all four samples right) went from 0.31 to 0.39. The model
got more consistent without getting more correct.

**The aggressive variant told us where the limit is.** Learning rate 1e-4,
no KL penalty, rank 32, 16 samples per prompt, from the base: its training
reward was no higher than the gentle rounds' after 250 steps, and each step
slowed as the policy explored. We stopped it. Whatever moves this model on
this task is not a bigger learning rate.

## The four things that made the loop worth running

1. **Rollouts through vLLM.** TRL's HF generation path took 65 seconds a
   step in thinking mode. Colocating vLLM in the trainer (`--use-vllm`) made a
   32-sample generation call about 40 seconds and an optimizer step 3 seconds,
   with three fixes on the way: vLLM 0.10's V0 engine for TRL 0.19's weight
   sync, torchrun's rank variables set for one process, and the old/reference
   log-prob pass chunked at the micro-batch, because scoring 32 sequences at
   once is 28 GB of logits.
2. **Gradient checkpointing off.** With it on, TRL generates without a KV
   cache, and on Qwen3-4B every training completion came out as random tokens
   with reward zero while a plain `model.generate` was fine. An easy way to
   train on garbage for an hour and read a flat curve as "the method does not
   work."
3. **Spawned launches.** A laptop network drop cancelled a three-hour
   `.remote()` call at step 49 even under `modal run --detach`. `--spawn`
   submits the call and returns; the run page is the client.
4. **Reply budgets for thinking models.** `simulate` capped replies at 2,048
   tokens and gave up after 60 seconds, which cut 8% of the base's answers
   mid-thought and lost 4 of 81 tasks. `agent_max_tokens=4096, timeout=300`
   are keywords now (zeroproof 0.47).

## What we would do next

In order: dynamic sampling so no step spends its batch on a unanimous group;
five to ten epochs at sixteen samples now that a round is minutes; a
bigger base, because RL amplifies what pass@k can already find and a 4B
tops out near 0.8 here. And the same table, every time, on the same
holdout. A hill climb you cannot check is a story.

## Reproduce it

```bash
pip install "zeroproof>=0.49" "psycopg[binary]" openai anthropic
git clone https://github.com/Zero-Proof-AI/zeroproof-sdk && cd zeroproof-sdk/recipes/04-train/text-to-sql
docker run -d -e POSTGRES_HOST_AUTH_METHOD=trust -p 5499:5432 postgres:16
psql -h 127.0.0.1 -p 5499 -U postgres -c "CREATE DATABASE shop" && psql -h 127.0.0.1 -p 5499 -U postgres -d shop -f schema.sql -f seed.sql
python rollout.py --hosted qwen3-4b-think --split holdout --k 4 && python build.py
PYTHONUTF8=1 modal run --detach train_grpo_modal.py --use-vllm --spawn --thinking --skip-eval --steps 300 --run-name my-r1
```

The README in the recipe has the rest, including how to swap in your own
schema and author tasks for it.
