# Teaching a Small Model to Write SQL for Your Database, and Checking Whether It Worked

**The short version.** We wanted to know whether a small open model can be
trained to write correct SQL for one specific database, and whether that
improvement can be proven rather than claimed. So we built a checker that
runs the model's query and compares the rows it returns to the right answer,
trained the model in rounds against that checker, and scored every round on
the same 140 questions it never saw during training. After three rounds the
first-try accuracy went from 58% to 61%. That is progress, but the
uncertainty band still reaches back to zero, so we do not call it proven yet.
Two other things improved clearly: the model stopped producing answers with
no query in them, and it got more consistent from one try to the next. All
the data and every trained checkpoint are public on Hugging Face at
[`zero-proof-ai/text-to-sql-shop`](https://huggingface.co/datasets/zero-proof-ai/text-to-sql-shop),
and the code is a recipe in the open-source
[whileai SDK](https://github.com/whilehq/whileai-sdk/tree/main/recipes/04-train/text-to-sql).

## What we built

**The database.** An online store: customers, products, orders, order
items, payments, reviews, employees, categories. Eight tables and 300
orders, generated by a script with a fixed seed so anyone can rebuild the
exact same database. It has the quirks real databases have: an order has no
ship date until it ships, a discount is empty when there was none, a
cancelled order has no payment, a refund is a second payment row, and
employees report to other employees.

**The questions.** 741 questions in plain English, each with the SQL query
that answers it correctly. They were written by Claude with the schema and
notes in front of it, across ten kinds of question (simple totals, top-N
lists, joins across two or more tables, date grouping, questions where an
empty value changes the answer, and so on) at three difficulty levels. Every
answer query was run twice and kept only if it returned a stable result of
one to fifty rows. 140 of the 741 were set aside as the test set. Nothing
ever trains on those.

**The checker.** It takes the model's reply, pulls out the SQL, runs it
against the database with a time limit, and compares the rows to the rows the
correct query returns. Same rows in any order counts as correct (unless the
question asked for an order). The model gets a 1 or a 0. No judge model, no
opinion, no partial credit for looking right.

**The scoring rule.** Every checkpoint answers each of the 140 test
questions four times. We report the average first-try accuracy, and because
140 questions is a small set, we report it with a 95% uncertainty band. When
we compare two checkpoints we compare them question by question, so the band
on the difference is honest too. If that band includes zero, we say the
change is not proven.

## First, is there anything to gain?

Before training, we measured how often the model gets a question right on
its first try, and how often it gets it right in at least one of four tries.
The gap between those two numbers is the room this kind of training can
work with: questions the model can already solve sometimes, just not
reliably.

| Model (first cut, 81 test questions) | right on first try | right in one of four tries |
|---|---|---|
| Qwen3-4B, reasoning turned off | 58% | 64% |
| Qwen3-4B, reasoning turned on | 69% | 81% |
| Claude Haiku 4.5 | 72% | 75% |
| Claude Sonnet 5 | 88% | 90% |

With reasoning off, the gap is six points, and training did nothing: two
different methods each moved the number by less than the uncertainty band.
With reasoning on, the gap is twelve points. So everything below trains and
tests the model with its reasoning turned on.

## Five checkpoints, one test

After the first cut we wrote 324 more questions of the kinds the model
struggled with (joins across three or more tables, self-joins, date buckets,
computed metrics), which grew the test set to 140 questions and tightened
the uncertainty band to about six points.

| Checkpoint | Trained from | What we did | Right on first try (95% band) | Right on all four tries | Reply contains a query |
|---|---|---|---|---|---|
| base | Qwen3-4B | nothing | 58% (52..64) | 31% | 86% |
| round 1 | base | 100 training steps | 58% (52..64) | 29% | 89% |
| round 2 | round 1 | 200 more steps, larger updates | 60% (54..67) | 34% | 90% |
| self-taught | base | fine-tuned on its own 199 correct answers | 60% (54..67) | 39% | 96% |
| round 3 | round 2 | 1,000 more steps, faster sampling | 61% (56..67) | 29% | 86% |

Each checkpoint's 560 test replies are a separate config in the Hugging Face
dataset (`eval-base`, `eval-r1`, and so on), and each trained checkpoint is
a model repo (`zero-proof-ai/text-to-sql-shop-r3` and so on), so every
number in this table can be recomputed by anyone.

## What we learned

**First-try accuracy moved a little, and only with a real dose of training.**
58, 58, 60, 61. Round 3 is three points better than the base, up at every
difficulty level and clearly up on date questions (43% to 58%), and the band
on the overall difference runs from minus two to plus seven. Better, and not
proven. We would rather say that than round it
up.

**Training scores rose faster than test scores.** Inside every round, the
model's success rate on the questions it was practicing on went up: round 1
from 49% to 63%, round 3 to 81% near the end. That is a familiar pattern. It
means the model learns the questions it is shown before it learns the
skill behind them, and with 336 practice questions and short rounds, most
of the early gain was that kind. Round 3, with 601 questions and three
passes over them, is where the test score started to follow.

**The cheap lessons come first.** In every round the model's reasoning got
shorter, from about 1,100 tokens to 800. Shorter thinking is the easiest way
to score better under a length limit. The self-taught checkpoint fixed a
different bad habit: the base model sometimes thinks at length and never
writes the query. That dropped from 14% of replies to 4%, the one change in
the table that is clearly outside the uncertainty band, and the model became
more consistent: all four tries right 39% of the time instead of 31%. More
consistent, not more correct.

**Pushing harder did not help.** We also tried a run with much larger
updates and no brake on how far the model drifts from its starting point. Its
training score was no better after 250 steps and each step got slower as it
wandered. We stopped it. Whatever moves this model on this task, it is not a
bigger learning rate.

## Five things that had to be fixed to keep going

1. **Sampling was the bottleneck.** The standard training loop generated the
   model's practice answers slowly: 65 seconds per step with reasoning on.
   Switching generation to a fast inference engine inside the trainer
   brought that to about ten seconds, which is the only reason round 3 was
   affordable.
2. **One memory-saving setting silently corrupted training.** With it on,
   every practice answer came out as random tokens and scored zero, while
   the same model answered fine outside the trainer. An easy way to train on
   garbage for an hour and conclude the method does not work.
3. **A dropped laptop connection cancelled a three-hour run** at step 49,
   even in the mode meant to survive that. Runs are now submitted and left
   alone; the training page is how you watch them.
4. **Reasoning models need room to think.** The SDK capped replies at 2,048
   tokens and gave up after 60 seconds, which cut 8% of the base model's
   answers off mid-thought. Both limits are now settings.
5. **Check what was sent to the model, not only what came back.** For a
   prompt-only agent the SDK invents a plausible tool list so its situation
   writer has a world to work in, and it was sending that list to the model
   under test as well. Qwen mostly ignored it; a Nemotron model called a
   made-up tool on every single question and scored zero, and 42 of round
   3's 560 test replies were tool calls. Fixed: a fixed task list never gets
   invented tools. The round 3 numbers above are the clean re-measure; the
   first measurement (62%) is kept alongside the data.

## What we would do next

Skip the practice questions the model already always gets right or always
gets wrong, so every step teaches something. Run five to ten passes over the
questions now that a round takes minutes. Try a bigger base model, since this
kind of training sharpens what a model can already do sometimes, and a
4-billion-parameter model tops out near 80% on these questions. And keep
scoring every checkpoint on the same 140 questions. A result you cannot
check is a story.

## Try it on your own database

```bash
pip install "whileai>=0.49" "psycopg[binary]" openai anthropic
git clone https://github.com/whilehq/whileai-sdk && cd whileai-sdk/recipes/04-train/text-to-sql
docker run -d -e POSTGRES_HOST_AUTH_METHOD=trust -p 5499:5432 postgres:16
psql -h 127.0.0.1 -p 5499 -U postgres -c "CREATE DATABASE shop" && psql -h 127.0.0.1 -p 5499 -U postgres -d shop -f schema.sql -f seed.sql
python rollout.py --hosted qwen3-4b-think --split holdout --k 4 && python build.py
```

The recipe's README explains how to swap in your own schema, write questions
for it, and run the same loop.
